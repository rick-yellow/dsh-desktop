# Decision Records

This reference defines the home for durable architectural rationale. Add a record when a change affects component ownership, runtime distribution, process lifecycle, security boundaries, persistence, or a repository-wide development rule.

Name records `YYYY-MM-DD-short-slug.md`. Use relative links to the affected source and documentation.

Each record contains these sections:

1. `Context` — constraints and facts that make the decision necessary.
2. `Decision` — the selected behavior and its owner, written in present tense after implementation.
3. `Alternatives and Trade-offs` — meaningful rejected options and what the choice gives up.
4. `Consequences` — operational, compatibility, security, and maintenance effects.
5. `Verification` — exact automated checks or observable behavior that protects the decision.

Decision records explain why the current mechanism exists. Keep task plans, acceptance checklists, incident chronology, and code walkthroughs in their owning systems rather than this directory.
